# VS Code integration (for discussion)

Status: **proposal, not scheduled** (recorded 2026-09-24). Pick up as a possible milestone 7.

## The question

Will VS Code on macOS treat msl distros as WSL remote targets?

**No.** The WSL extension (`ms-vscode-remote.remote-wsl`) is Windows-only: it runs `wsl.exe`, uses `\\wsl$` paths, and doesn't load on macOS. It has no setting for a different command. (This is based on how the extension works; we haven't tested it.)

## Options

### A. Remote-SSH (works today, manual)
Install `openssh-server` in the distro and run it on a port other than 22. msl's localhost forwarding exposes the port on the Mac, and VS Code Remote-SSH connects to `localhost:<port>`. Downsides: every distro needs sshd and its own port. Not yet tested with VS Code.

### B. SSH config generated by msl (recommended first step)
msl writes one `Host <distro>.msl` entry per distro to `~/.ssh/config`, with a `ProxyCommand` that goes through msld and vsock straight into that distro. No ports are opened on the Mac. Remote-SSH then lists every distro by name, and `ssh Ubuntu.msl` works.

Two ways to build it:
- msld starts the distro's own `sshd -i` (inetd mode) for each connection. The distro needs `openssh-server`, but no daemon has to keep running.
- A small SSH server built into msld or the guest agent, which authenticates with the Mac user's key and logs in as the distro's default user. Nothing needs installing in the distro. This is roughly what OrbStack does.

Possible CLI: automatic, or `msl --manage <distro> --ssh`.

### C. Our own WSL-style remote extension (not recommended)
Blockers:
- **Proposed API.** Remote connections go through VS Code's `resolvers` API, which is still proposed. Stable VS Code only allows it for allowlisted Microsoft extensions. Users would have to add `"enable-proposed-api": ["<publisher>.msl"]` to `~/.vscode/argv.json`, and the Marketplace rejects extensions that depend on proposed APIs, so we could only ship a `.vsix`.
- **Server licence.** The VS Code Server that runs inside the remote is licensed for use with Microsoft's remote extensions. `open-remote-ssh` and `open-remote-wsl` (jeanp413, for VSCodium) work around this with the open-source server build. That gives full VSCodium support but a grey area for VS Code.
- **Upkeep.** The resolver API changes with VS Code releases.

### D. Thin "MSL" extension on top of Remote-SSH (recommended second step)
Uses only the stable API, can be published on the Marketplace, and depends on B:
- an **MSL** section in Remote Explorer listing distros with their state and logo (from `msl -l -v`);
- commands to start or terminate a distro and to set the default;
- "Connect in current/new window": opens `vscode-remote://ssh-remote+<distro>.msl/home/<user>`;
- "Reopen Folder in MSL": maps a Mac folder to `/mnt/mac/...`;
- a status bar item showing `MSL: <distro>`.

The only visible difference from WSL is that the window's remote label shows SSH.

### E. `code .` inside a distro (needs a decision)
WSL does this by running Windows programs from Linux, which msl rules out ([architecture](../architecture.md), "Running Windows `.exe` from Linux"). An alternative that never runs a Mac binary: a Linux `code` script asks msld over vsock to open the folder in VS Code on the Mac. It still relaxes the "no Mac from Linux" rule slightly, so it needs a decision.

### F. `code tunnel` inside the distro
Works today, but needs a GitHub or Microsoft login and goes through Microsoft's relay. Not a default.

## Suggested order
B → D → (optional) E.

## Open questions
- sshd in the distro (`sshd -i`) or an SSH server built into msl?
- Write `~/.ssh/config` automatically, or on request? (Use an `Include ~/.ssh/msl_config` line rather than editing the user's file directly.)
- Whether to allow `code .` (E).
- Check whether Remote-SSH handles `ProxyCommand` hosts with a `.msl` suffix and the platform it detects in the distro (it should detect linux-arm64).
